
\chapter{Background}\label{ch:ch02:background}

In the introduction, we discussed what empirical performance prediction means and gave examples of how it is used. In this chapter, we first look more closely at what goes into a performance model and what it can predict. We then introduce two of its use cases, algorithm selection and Bayesian optimisation. The problems and benchmarks on which we study these methods are introduced in~\cref{ch:ch03:scenarios}.

\section{Empirical Performance Prediction}
\label{sec:ch02:empirical_performance_prediction}

First, we need to specify whose performance we wish to predict and on which problem. Let $\algo$ be a parameterised algorithm from a set of algorithms $\algorithmSpace$. A configuration $\configuration\in\configurationSpace$ assigns values to the parameters of $\algo$. For an instance $\instance\in\instanceSpace$, we write its features as $\instanceFeatures = [\instanceFeature_1, \ldots, \instanceFeature_{d_z}]^{\top} \in \mathbb{R}^{d_z}$. These features describe the instance to the model.

We denote the performance of $\algo$ with configuration $\configuration$ on $\instance$ by $\performanceVector \in \mathbb R^{d_p}$, where $d_p \in \mathbb N$ is the number of metrics we measure. For example, if we care only about the running time of a \gls{sat} solver, this vector has one element. If we care about both the accuracy and the inference speed of a neural network, it has two. In the latter case, a configuration that improves one metric may come at the cost of the other.

For a single metric $\performance$, we write an \gls{epm} as a learned function
\begin{equation}
  \hat{f} : \modelInput \mapsto \performance.
\end{equation}
As discussed in the introduction, the input $\modelInput$ depends on which quantities vary across observations. We distinguish three common settings.

\begin{itemize}
  \item \textbf{Per-instance.} We keep the configuration fixed, usually at its default, and use instance features as the input, $\modelInput = \instanceFeatures$. For example, a selector such as SATzilla can use these features to predict how long a solver will take on a new instance~\citep{XuEtAl08}.
  \item \textbf{Per-configuration.} We keep the instance or set of instances fixed and vary the configuration, so $\modelInput = \configuration$. This setting is common in \gls{hpo}~\citep{FeuEtAl19} and \gls{nas}~\citep{ElsEtAl19}.
  \item \textbf{Per-configuration-and-instance.} When both vary, we give the model both inputs, $\modelInput = (\configuration, \instanceFeatures)$. This is useful, for example, when configuring an algorithm for a set of instances with different properties~\citep{HutEtAl14,EggEtAl18}.
\end{itemize}

In practice, collecting performance data introduces several difficulties. First, we may evaluate several configurations on the same instance or run one configuration across several instances. Observations that share an instance or a configuration may be related, so treating all observations as independent can be misleading. Second, running times can vary by orders of magnitude and can have a long right tail. If we stop a run at a time limit, we only know that its running time exceeds that limit.

Finally, when an algorithm uses randomness, repeated runs with the same inputs can give different outcomes. We may have only a few observations from which to learn, particularly when each run is expensive. The scale of the target can also vary across scenarios, which affects whether a transformation such as taking the logarithm is useful.

So far, we have treated the prediction as a single number for each metric, such as the mean or median running time. If we also want to know how much the running time varies or how often very long runs occur, we can predict a conditional distribution $\rho(y \mid \modelInput)$~\citep{EggEtAl18a}. We describe this setting below.

\subsection{Applications and Instance Features}

\glspl{epm} have been developed for a wide range of tasks, including automated algorithm selection~\citep{XuEtAl08, Kotthoff16}, algorithm configuration and parameter tuning~\citep{HutEtAl12, HutEtAl06}, data centre and cloud scheduling~\citep{LeeEtAl25, IslEtAl12, SaxEtAl23, PhaEtAl20}, compiler optimisation~\citep{YotEtAl03, AshEtAl19}, and database query optimisation~\citep{WuEtAl13}. \glspl{epm} require a set of features describing instances as an input to the model. For $\mathcal{NP}$-complete problems, high-level properties of instances are encoded to serve as an instance identifier, such as the SATzilla features for \gls{sat}~\citep{HutEtAl14,ShaHoo24} and causal-graph or planning-graph features for automated planning~\citep{FawEtAl14}.

\subsection{Performance Distribution Prediction}
\label{sec:ch02:distribution_prediction}

Consider running the same stochastic solver more than once on a given instance. Even with the same configuration, different random choices can lead to different running times. Let $\xi$ denote the random choices made during a run. Once we fix the solver $\algo$, configuration $\configuration$, and instance $\instance$, we can write the running time and the probability of finishing by time $u$ as
\begin{equation*}
    T_{\algo,\configuration,\instance}
    = \tau(\algo,\configuration,\instance,\xi),
    \qquad
    F_{\algo,\configuration,\instance}(u)
    = \Pr(T_{\algo,\configuration,\instance}\leq u),
    \quad u\geq 0.
\end{equation*}
Here, $\tau$ measures the elapsed time until the solver reaches its termination criterion. If the solver never reaches it, we can assign that run infinite running time. The cumulative distribution function $F$ then tells us the probability that the solver finishes within $u$ units of time. A distributional \gls{epm} estimates this distribution from instance features and, when the configuration varies, from the configuration as well~\citep{EggEtAl18}.

As previously mentioned, we often stop a solver after a time limit $\runtimeCutoff$. In that case, we record both the time spent on the run and whether the solver finished. We write these observations as
\begin{equation*}
    \widetilde T = \min\{T_{\algo,\configuration,\instance},\runtimeCutoff\},
    \qquad
    \delta = \mathbf 1\{T_{\algo,\configuration,\instance}\leq\runtimeCutoff\}.
\end{equation*}
When $\delta=0$, we only know that the running time exceeds $\runtimeCutoff$. We refer to such an observation as \emph{right-censored}.

Traditional \glspl{epm} handle this stochasticity by either modelling an aggregate statistic calculated from repeated runs (\emph{e.g.}, the empirical mean or median) or training directly on noisy, single-run observations. In both cases, the \gls{epm} outputs a single scalar value, discarding all information about the variance and shape of the underlying distribution.

To capture the complete run-to-run variation of stochastic algorithms, \citet{EggEtAl18} introduced \emph{DistNet}, a neural network that predicts the parameters of a per-instance running time distribution (\emph{e.g.}, a log-normal distribution). DistNet is trained by minimising the \gls{nll} of individual run observations, which is more efficient and numerically stable than a two-stage approach that first fits distribution parameters per instance and then regresses on those parameters.

To improve predictive quality in data-scarce regimes, \emph{BayesDistNet}~\citep{TueBur21} replaces the deterministic network with a \Gls{bnn}. During inference, BayesDistNet generates running-time samples by repeatedly evaluating the \gls{bnn} with different weight samples, subsequently fitting a parametric distribution post-hoc. While effective with few training runs, this sampling-based inference introduces substantial computational overhead. Furthermore, because \gls{bnn} predictions rely on stochastic weight samples, feature attribution becomes unstable and computationally prohibitive, making it ill-suited for explainability.

\section{Algorithm Selection}
\label{sec:ch02:algorithm_selection}

In this section, we introduce the algorithm selection problem and its components, including a formal definition, common baselines and use cases. We also relate it to multi-class classification and empirical performance prediction.

\subsection{Formal Definition}
Given a set of problem instances $\instanceSpace$ (which can be, for example, datasets), instance features $\featureSpace$, a set of algorithms $\algorithmSpace$ and a performance metric $p:\algorithmSpace \times \instanceSpace \rightarrow \mathbb{R}$ (for example, predictive accuracy or running time), the algorithm selection problem~\citep{Rice76} seeks to find a selector $S:\featureSpace\rightarrow\algorithmSpace$ such that the performance of $S$ on the instances $\instanceSpace$ is optimal according to $p$~\citep{KerEtAl19}.

Extensions include the use of \textit{algorithm features}, which are combined with the instance features to predict the best algorithm for each problem instance. For simplicity, for the remainder of the section, we assume that the goal is to minimise $p$.
In algorithm selection, the ideal goal is to reach the performance of the \gls{vbs} (\emph{i.e.}, perfect selector). Furthermore, the selection must be better than the \gls{sbs} in order to make the use of algorithm selection worthwhile.

Algorithm selection methods are integrated into \textit{algorithm selection pipelines}, which include several components:
\begin{itemize}
    \item \textbf{Pre-selection:} A subset of algorithms is selected from a larger candidate set. In most real-world scenarios, only a few algorithms contribute substantially to \gls{vbs} performance, yet having many candidates to choose from makes accurate selection harder and increases the risk of poor predictions. Pre-selection constructs a small, complementary portfolio. A prominent method for pre-selection is greedy selection based on marginal contributions~\citep{XuEtAl08}, where algorithms are iteratively added to the portfolio if they yield the largest improvement to the \gls{vbs} performance.

    \item \textbf{Pre-solving schedules:} For problems where the metric of interest is running time (e.g., $\mathcal{NP}$-complete problem solving), it is beneficial to first run a short schedule (\emph{i.e.}, a sequence of solvers, each executed with a specific cut-off time) of solvers to solve easy instances quickly, thereby avoiding unnecessary feature computation. Such methods use, for example, a greedy method to decide which algorithms to run~\citep{XuEtAl08}, or use an optimisation problem to find the optimal pre-solving schedule~\citep{HooEtAl12,KadEtAl11}.

    \item \textbf{Algorithm selection:} An algorithm (or a schedule of algorithms) is selected based on the computed features. This step typically involves a machine learning model. For example, there can be models that predict the performance for each instance~\citep{XuEtAl08,OztEtAl22}, models that predict the ranking of the algorithms~\citep{XuEtAl12,KerEtAl18}, formulating the problem as a recommendation task~\citep{MisSeb17} and other approaches.

\end{itemize}
Additionally, for algorithm selection, there is a need for two additional, problem specific components:
\begin{itemize}
    \item \textbf{Feature computation:} Representative features of the problem instance are computed and used as input to the learned selector. These features can be hand-crafted or learned from the data. The choice of features is crucial for the performance of the algorithm selector. For example, the SATzilla features are well-known to be a good representation of \gls{sat} instances~\citep{HutEtAl14,ShaHoo24}, while for machine learning datasets, there exists many features, such as the basic descriptors of~\citet{OztEtAl22} to more complicated features, that include advanced statistics, such as the ones implemented in PyMFE~\citep{AlcEtAl20}.

    \item \textbf{Evaluation metric:} This is an important component of algorithm selection, as it is used to evaluate the performance of the algorithm selector. While there exist broadly applicable metrics such as the performance of the \gls{vbs} and \gls{sbs}, their definition depends on the specific problem.

    Therefore, a problem-specific evaluation metric must be chosen that represents the performance of the algorithm. This can be, for example, accuracy, precision, recall, F1-score, \gls{auc}, running time and more, depending on the use-case.
\end{itemize}
An overview of the algorithm selection pipeline is presented in~\cref{fig:ch02:asf_pipeline}.

\subsection{Algorithm Selection versus Multi-Class Classification}
A common mistake among newcomers to algorithm selection is to treat it as a standard multi-class classification problem.
Although an algorithm selector predicts one algorithm from a finite set and

can therefore be seen as performing a multi-class prediction task, training it as an ordinary multi-class classifier can yield sub-par performance, because it discards the performance of the algorithms relative to each other.

To see why, consider an instance where the performance gap between the best and the second-best algorithm is small.
In that case, selecting the second-best algorithm is a reasonable error.
A plain multi-class classifier, however, treats this outcome as equally wrong as choosing an algorithm that performs very poorly on the instance.
As we show in our ASlib experiments (\cref{sec:ch10:aslib_appendix}), multi-class classifiers can indeed perform far below the other methods in practice.

\subsection{Performance Prediction versus Ranking}

To model performance, one should account for the distribution of the performance, which can require preprocessing of the labels, such as log-transformation~\citep{HutEtAl14}. However, \gls{epm}-based algorithm selection is often not the practically best approach, essentially because accurately predicting exact performance values is generally a harder task than determining the relative ranking of algorithms.

\section{Bayesian Optimisation}
\label{sec:ch02:bayesian_optimisation}

In the introduction, we saw that tuning a learning algorithm can improve its performance. We will now define the tuning problem and show how Bayesian optimisation uses predictions to choose which configuration to try next. We use this setting in~\cref{ch:ch06:dymbo,ch:ch08:noisy_oracle}.

\subsection{Hyperparameter Optimisation}
\label{sec:ch02:hpo}

The goal of \new{\gls{hpo}} is to find the settings of a learning algorithm that give the lowest validation loss~\citep{BisEtAl23}. To define this task, let $\algo$ be the learning algorithm and $\configurationSpace$ its hyperparameter configuration space. We fix the training data $\mathcal D_{\mathrm{train}}$ and the validation data $\mathcal D_{\mathrm{validate}}$. For a configuration $\configuration\in\configurationSpace$, we denote the algorithm with those settings by $\algo_{\configuration}$. The objective and its minimiser are given by
\begin{equation}
\label{eq:ch02:def-hpo}
    f(\configuration) =
    \mathcal L(\algo_{\configuration},\mathcal D_{\mathrm{train}},
    \mathcal D_{\mathrm{validate}}),
    \qquad
    \configuration^* \in \argmin_{\configuration\in\configurationSpace}
    f(\configuration).
\end{equation}
Here, $\mathcal L$ is the loss we obtain by training on $\mathcal D_{\mathrm{train}}$ and evaluating the fitted model on $\mathcal D_{\mathrm{validate}}$. If we use cross-validation, we average the loss over multiple training and validation splits. If training uses randomness, different runs with the same configuration can produce different losses. In this case, we can optimise the expected validation loss.

What does a configuration contain? For example, it can specify a continuous learning rate, an integer number of trees, or a categorical choice of model family. The choice of family can affect which other hyperparameters are active. For $d_c$ hyperparameters with domains $\mathcal C_h$, we therefore have $\configurationSpace\subseteq\mathcal C_1\times\cdots\times\mathcal C_{d_c}$. For independent, unconstrained parameters, the space is the full product. Conditions and constraints can restrict which configurations are admissible.

For each configuration we try, we usually have to train and validate a model. This can make a single evaluation expensive and motivates using the results of previous evaluations to choose which configuration to try next.

\subsection{Bayesian Optimisation}
\label{sec:ch02:bac_bo}

\Gls{bo}~\citep{Mockus12b,Garnett23,Frazier18b,Kushner62,Kushner64b} is a family of surrogate-based algorithms for efficient global optimisation of black-box problems.
As in \gls{hpo}, we want to minimise an objective $f:\configurationSpace\rightarrow\mathbb R$ over $\configurationSpace$. We can evaluate $f$ at configurations of our choice. The optimiser has access to these evaluations and works without an analytical expression or derivatives of $f$. With a budget of $B_{\mathrm{eval}}$ evaluations, it can try $n_{\mathrm{eval}}\leq B_{\mathrm{eval}}$ configurations and use earlier observations to choose later ones. When the evaluations are noiseless, we call the best configuration observed so far the \emph{incumbent} and write it as
\begin{equation*}
    \configuration^{\mathrm{inc}} \in
    \argmin_{\configuration\in
    \{\configuration^{(1)},\ldots,\configuration^{(n_{\mathrm{eval}})}\}}
    f(\configuration).
\end{equation*}
In practice, we might have a limit on wall-clock time instead of a fixed number of evaluations. If evaluations are noisy, the value we observe is one random outcome and we can define the objective as its expectation. In either case, we have to decide how much of the budget to spend exploring unfamiliar regions and how much to spend near configurations that already look promising~\citep{Garnett23}.

Typically, \gls{bo} consists of three main components: an \emph{initial design}, \emph{i.e.}, in \gls{hpo}, a set of candidate hyperparameter configurations $\mathcal C_{\mathrm{obs}} = (\configuration^{(1)},\ldots, \configuration^{(n_0)})$ and their evaluations
$f(\mathcal C_{\mathrm{obs}}) = (f(\configuration^{(1)}),\ldots, f(\configuration^{(n_0)}))$; a \emph{surrogate model} (fitted to the
observations) that returns an approximation $\hat{f}(\configuration)$ of the unknown loss function $f(\configuration)$ while capturing the uncertainty in the prediction $\hat{\sigma}(\configuration)$ on unobserved points in the search space; and an \emph{acquisition function}, which is optimised to suggest candidate solutions to be evaluated next, usually balancing exploration and exploitation of the search space.
\gls{bo} then evaluates the most promising candidate solutions.
To approximate the expensive objective function, \gls{bo} typically employs a \Gls{gp} model as the surrogate. The \gls{gp} model defines a distribution over functions on the configuration space $f(\configuration)\sim\mathcal{GP}_f(\mu(\configuration),k_{\mathrm{GP}}(\configuration,\configuration'))$, where
$\mu(\cdot)$
is a mean function and
$k_{\mathrm{GP}}(\cdot,\cdot)$
is a covariance function. If we consider an observation model
$y_j = f(\configuration^{(j)}) + \varepsilon_j$
with normally distributed noise,
$\varepsilon_j\sim\mathcal{N}(0,\sigma^2_\varepsilon)$,
the predicted value by the \gls{gp} model at one unknown configuration
$\configuration$ will also follow a normal distribution with mean
$\mu(\configuration)=\mathbf K_{\configuration,\mathcal C_{\mathrm{obs}}}(\mathbf K_{\mathcal C_{\mathrm{obs}},\mathcal C_{\mathrm{obs}}}+\sigma^2_\varepsilon \mathbf I)^{-1}\mathbf y$ and variance $\sigma^2(\configuration)=k_{\mathrm{GP}}(\configuration,\configuration)-\mathbf K_{\configuration,\mathcal C_{\mathrm{obs}}}(\mathbf K_{\mathcal C_{\mathrm{obs}},\mathcal C_{\mathrm{obs}}}+\sigma^2_\varepsilon \mathbf I)^{-1} \mathbf K_{\mathcal C_{\mathrm{obs}},\configuration}$,
where $\mathbf y=(y_1,\ldots,y_{n_0})$ is the vector of observations, $\mathbf K_{\mathcal C_{\mathrm{obs}},\mathcal C_{\mathrm{obs}}}=[k_{\mathrm{GP}}(\configuration^{(j)},\configuration^{(j\prime)})]_{\configuration^{(j)},\configuration^{(j\prime)}\in\mathcal C_{\mathrm{obs}}}$ is the covariance matrix, and $\mathbf K_{\configuration,\mathcal C_{\mathrm{obs}}}=[k_{\mathrm{GP}}(\configuration^{(j)},\configuration)]_{\configuration^{(j)}\in\mathcal C_{\mathrm{obs}}}$ is the correlation vector for all samples.
\glspl{gp} as a surrogate model inherently provide both the mean and the variance vector.

However, \glspl{gp} are not the only surrogate model used in \gls{bo}. Another common choice for a surrogate model are tree-based models,
such as \glspl{rf}.
Tree-based models traditionally predict only the mean of the given data (\emph{e.g.}, in a regression setting).
In this case, the variance is defined based on the variance of the predictions of the leaves~\citep{HutEtAl11}.
With $e_{\mathrm{RF}}(\configuration)$ being the prediction of a tree $e_{\mathrm{RF}} \in \mathcal E_{\mathrm{RF}}$, we calculate the mean $\mu(\configuration)$ and variance $\sigma^2(\configuration)$ for a set of trees $\mathcal E_{\mathrm{RF}}$ as follows:
\begin{equation}
    \mu(\configuration)=\frac{1}{|\mathcal E_{\mathrm{RF}}|} \cdot \sum_{e_{\mathrm{RF}}\in \mathcal E_{\mathrm{RF}}} e_{\mathrm{RF}}(\configuration) \; ,
\end{equation}
\begin{equation}
    \sigma^2(\configuration)=\frac{1}{|\mathcal E_{\mathrm{RF}}|} \cdot \sum_{e_{\mathrm{RF}}\in \mathcal E_{\mathrm{RF}}} (e_{\mathrm{RF}}(\configuration) - \mu(\configuration))^2 \; .
\end{equation}
\gls{bo} proceeds iteratively until a termination criterion is met. In each iteration, it optimises the acquisition function by repeatedly querying the surrogate model to generate a pool of candidate solutions. It then evaluates the most high-potential solutions (\emph{i.e.}, the solutions that maximise the acquisition function) from this pool,
refines the surrogate model based on the new observations, and updates the optimum if the new point improves upon the true function value of the best observation so far.

\subsection{Acquisition Functions}
\label{sec:ch02:acquisition_functions}

We now look at how an acquisition function turns the predictions of a surrogate into a decision about where to sample next. We use the notation of~\cref{ch:ch08:noisy_oracle}.

Given a black-box function $f:\sR^{d_c}\rightarrow\sR$, the goal of an optimiser is to find its minimum, denoted by $\configuration^*$, such that $f(\configuration^*)\leq f(\configuration)$ for every $\configuration\in\sR^{d_c}$. The optimiser iteratively samples configurations $\configuration_1, \configuration_2, ..., \configuration_n$, where $\configuration_t$ is the configuration sampled at iteration $t$.
At each iteration, the optimiser observes the performance $f(\configuration_t)$, producing the set of observations $\train=\{(\configuration_1, f(\configuration_1)), (\configuration_2, f(\configuration_2)),..., (\configuration_n, f(\configuration_n))\}$.

Bayesian optimisation~\citep{Garnett23} uses a surrogate model to decide on the next configuration to sample. At iteration $t$, the surrogate model $m$ takes an unseen configuration $\configuration$ together with the observation set $\train$ and estimates a predictive distribution for $\configuration$, typically summarised through a mean $\mu_m(\configuration)$ and variance $\sigma_m^2(\configuration)$.
\glspl{gp} are a common choice for such a surrogate model, but random forests~\citep{HutEtAl11} and other machine-learning techniques that can provide uncertainty estimates are also used.

Following the fitting of a surrogate model, an acquisition function is used to determine the next point to sample, balancing exploration and exploitation by considering the predicted mean and variance. Here, we consider three popular acquisition functions. First, \gls{ei} quantifies the expected improvement in the known optimum by sampling a configuration $\configuration$; formally:
\begin{multline}
    EI(\configuration)=\mathbb{E}[max(0, f(\configuration^{\mathrm{inc}})-\mu_m(\configuration))]=\\(f(\configuration^{\mathrm{inc}})-\mu_m(\configuration))\cdot\Phi(\zeta)+\sigma_m(\configuration)\cdot\phi(\zeta)
\end{multline}

\begin{equation*}
    \zeta=\frac{f(\configuration^{\mathrm{inc}})-\mu_m(\configuration)}{\sigma_m(\configuration)},
\end{equation*}
where $f(\configuration^{\mathrm{inc}})=\min_{j=1, 2, ..., n} f(\configuration _j)$ is the best observed function value up to iteration $n$, also known as the incumbent.
Similarly, \gls{pi} quantifies the probability that configuration $\configuration$ improves over the known optimum:
\begin{equation*}
    PI(\configuration)=\Pr(f(\configuration^{\mathrm{inc}})-\mu_m(\configuration) > 0)=\Phi(\zeta)
\end{equation*}
Finally, the \gls{lcb} is the weighted sum of the predicted performance $\mu_m(\configuration)$ and the uncertainty $\sigma(\configuration)$:
\begin{equation*}
    LCB(\configuration)=-(\mu_m(\configuration)-\beta_{\mathrm{LCB}}\sigma_m(\configuration))
\end{equation*}

The acquisition function $\alpha_t$ is then optimised to find a candidate configuration $\configuration_{\mathrm{next}} \in \argmax_{\configuration\in\sR^{d_c}}\alpha_t(\configuration)$. Different methods have been proposed to optimise the acquisition function, including local search, evolutionary algorithms and gradient-based methods. Since evaluating the acquisition function is relatively cheap, many such evaluations can be used to obtain a strong candidate. The candidate is then evaluated on the target function $f$, after which $\train$ is updated as $\train=\train \cup \{(\configuration_{\mathrm{next}}, f(\configuration_{\mathrm{next}}))\}$. This process continues until a pre-defined evaluation budget is exhausted.
