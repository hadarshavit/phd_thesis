\section{Empirical performance prediction}
\label{sec:ch02:empirical_performance_prediction}

Let $\algo$ denote a parameterised algorithm drawn from an algorithm space $\algorithmSpace$, and let $\configuration \in \configurationSpace$ be a configuration, \emph{i.e.}, an assignment of values to the parameters of $\algo$. Let $\instance\in \instanceSpace$ denote a problem instance out of the instance space $\instanceSpace$. $\instance$ is characterised by a feature vector $\instanceFeatures = [\instanceFeature_1, \ldots, \instanceFeature_{d_z}]^{\top} \in \mathbb{R}^{d_z}$. The performance of $\algo$ using configuration $\configuration$ on $\instance$ is denoted by $\performanceVector \in \mathbb{R}^{d_p}$, $d_p \in \mathbb{N}$. Note that, $\performanceVector$ can be have a single element, if there is only one performance metric of interest (for example, the running time of a SAT solver), or, have multiple, potentially competing performance metrics (for example, accuracy and inference speed of a neural network).

An empirical performance model (EPM) is a learned function
\begin{equation}
  \hat{f} : \modelInput \mapsto \performance,
\end{equation}
where the input $\modelInput$ depends on the observation type. There are three common types of inputs to and EPM:

\begin{itemize}
  \item \textbf{Per-instance.} The algorithm is executed with a fixed (usually the default) configuration, and performance is predicted from instance features alone: $\modelInput = \instanceFeatures$. Such setting is commonly is in algorithm selectors such as SATzilla~\citep{XuEtAl08}.
  \item \textbf{Per-configuration.} The algorithm is evaluated on a fixed instance or a fixed set of instances, and performance is predicted from the configuration parameters: $\modelInput = \configuration$. This is the case in HPO~\citep{FeuEtAl19} and NAS~\citep{ElsEtAl19}.
  \item \textbf{Per-configuration-and-instance.} The input for the model consists of both configuration and instance features: $\modelInput = (\configuration, \instanceFeatures)$. This most general setting and is used, for example, in algorithm configuration~\citep{HutEtAl14,EggEtAl18}.
\end{itemize}
A key challenge that distinguishes EPMs from standard regression problems is the structure of the observed data. Performance observations are usually not independent: multiple configurations may be evaluated on the same problem instance (or vice versa), introducing group structure that violates the i.i.d.\ assumption. Additionally, a common performance metric, running time, frequently exhibit heavy-tailed, right-skewed distributions, requiring special treatment. 
The problem becomes more severe, as running time observations have a cutoff, meaning that the algorithms are ran until a certain time limit. 
This means that, for some runs of the algorithm, we don't know the exact running time, but simply that it is larger than the cutoff.
Moreover, performance data is usually noisy, as many algorithms use randomness, and, as data is scarce, it is necessary to learn a meaningful predictor from few observations. Performance observations are usually not independent: multiple configurations may be evaluated on the same problem instance (or vice versa), introducing group structure that violates the i.i.d.\ assumption. 
Finally, across different scenarios, the scale of the performance target can vary by many orders of magnitude, so preprocessing choices that are beneficial in one scenario may be harmful in another. 




The predict performance can be a single number per metric, showing the mean or median value. Alternatively, it is also possible to predict the full performance distribution distribution $\rho(y \mid \modelInput)$ rather than a single value to obtain a distributional EPM~\citep{EggEtAl18a}, which is particularly valuable for capturing more subtle details of the performance of the algorithm, such as its variance and skewness.
\subsection{Applications and instance features}

EPMs have been developed for a wide range of tasks, including automated algorithm selection~\citep{XuEtAl08, Kotthoff16}, algorithm configuration and parameter tuning~\citep{HutEtAl12, HutEtAl06}, data centre and cloud scheduling~\citep{LeeEtAl25, IslEtAl12, SaxEtAl23, PhaEtAl20}, compiler optimisation~\citep{YotEtAl03, AshEtAl19}, and database query optimisation~\citep{WuEtAl13}. EPMs require a set of features describing instances as an input to the model. For $\mathcal{NP}$-complete problems, high-level properties of instances are encoded to serve as an instance identifier, such as the SATzilla features for propositional satisfiability (SAT)~\citep{HutEtAl14,ShaHoo24} and causal-graph or planning-graph features for automated planning~\citep{FawEtAl14}.

\subsection{Performance distribution prediction}
\label{sec:ch02:distribution_prediction}

For a stochastic solver, repeated runs on a fixed instance need not take the same amount of time. Let $\xi$ denote the random choices made during a run. For a fixed solver $\algo$, configuration $\configuration$, and instance $\instance$, its running time is a random variable
\begin{equation*}
    T_{\algo,\configuration,\instance}
    = \tau(\algo,\configuration,\instance,\xi),
    \qquad
    F_{\algo,\configuration,\instance}(u)
    = \Pr(T_{\algo,\configuration,\instance}\leq u),
    \quad u\geq 0,
\end{equation*}
where $\tau$ is the elapsed time to the solver's termination criterion and $F$ is the cumulative distribution function. A run that never reaches that criterion can be assigned infinite running time. Distribution prediction seeks to estimate this conditional distribution from instance features and, where they vary, algorithm configurations, rather than predicting only an aggregate such as the mean~\citep{EggEtAl18}.

If a run is stopped at a cutoff $\runtimeCutoff$, the recorded observation can be expressed as
\begin{equation*}
    \widetilde T = \min\{T_{\algo,\configuration,\instance},\runtimeCutoff\},
    \qquad
    \delta = \mathbf 1\{T_{\algo,\configuration,\instance}\leq\runtimeCutoff\}.
\end{equation*}
When $\delta=0$, the run is right-censored: its exact running time is unknown, but exceeds the cutoff.

Traditional EPMs handle this stochasticity by either modelling an aggregate statistic calculated from repeated runs (\emph{e.g.}, the empirical mean or median) or training directly on noisy, single-run observations. In both cases, the EPM outputs a single scalar value, discarding all information about the variance and shape of the underlying distribution.

To capture the complete run-to-run variation of stochastic algorithms, \citet{EggEtAl18} introduced \emph{DistNet}, a neural network that predicts the parameters of a per-instance running time distribution (\emph{e.g.}, a log-normal distribution). DistNet is trained by minimising the negative log-likelihood (NLL) of individual run observations, which is more efficient and numerically stable than a two-stage approach that first fits distribution parameters per instance and then regresses on those parameters.

To improve predictive quality in data-scarce regimes, \emph{BayesDistNet}~\citep{TueBur21} replaces the deterministic network with a Bayesian neural network (BNN). During inference, BayesDistNet generates running-time samples by repeatedly evaluating the BNN with different weight samples, subsequently fitting a parametric distribution post-hoc. While effective with few training runs, this sampling-based inference introduces substantial computational overhead. Furthermore, because BNN predictions rely on stochastic weight samples, feature attribution becomes unstable and computationally prohibitive, making it ill-suited for explainability.

\section{Algorithm selection}
\label{sec:ch02:algorithm_selection}

In this section, we introduce the algorithm selection problem and its components, including a formal definition, common baselines and use cases. We also relate it to multi-class classification and empirical performance prediction.

\subsection{Formal definition}
Given a set of problem instances $\instanceSpace$ (which can be, for example, datasets), instance features $\featureSpace$, a set of algorithms $\algorithmSpace$ and a performance metric $p:\algorithmSpace \times \instanceSpace \rightarrow \mathbb{R}$ (for example, predictive accuracy or running time), the algorithm selection problem~\citep{Rice76} seeks to find a selector $S:\featureSpace\rightarrow\algorithmSpace$ such that the performance of $S$ on the instances $\instanceSpace$ is optimal according to $p$~\citep{KerEtAl19}.

Extensions include the use of \textit{algorithm features}, which are combined with the instance features to predict the best algorithm for each problem instance. For simplicity, for the remainder of the section, we assume that the goal is to minimise $p$.
In algorithm selection, the ideal goal is to reach the performance of the \gls{vbs} (\emph{i.e.}, perfect selector). Furthermore, the selection must be better than the single best solver (\gls{sbs}) in order to make the use of algorithm selection worthwhile.

Algorithm selection methods are integrated into \textit{algorithm selection pipelines}, which include several components:
\begin{itemize}
    \item \textbf{Pre-selection:} A subset of algorithms is selected from a larger candidate set. In most real-world scenarios, only a few algorithms contribute substantially to \gls{vbs} performance, yet having many candidates to choose from makes accurate selection harder and increases the risk of poor predictions. Pre-selection constructs a small, complementary portfolio. A prominent method for pre-selection is greedy selection based on marginal contributions~\citep{XuEtAl08}, where algorithms are iteratively added to the portfolio if they yield the largest improvement to the \gls{vbs} performance.

    \item \textbf{Pre-solving schedules:} For problems where the metric of interest is running time (e.g., $\mathcal{NP}$-complete problem solving), it is beneficial to first run a short schedule (\emph{i.e.}, a sequence of solvers, each executed with a specific cut-off time) of solvers to solve easy instances quickly, thereby avoiding unnecessary feature computation. Such methods use, for example, a greedy method to decide which algorithms to run~\citep{XuEtAl08}, or use an optimisation problem to find the optimal pre-solving schedule~\citep{HooEtAl12,KadEtAl11}.

    \item \textbf{Algorithm selection:} An algorithm (or a schedule of algorithms) is selected based on the computed features. This step typically involves a machine learning model. For example, there can be models that predict the performance for each instance~\citep{XuEtAl08,OztEtAl22}, models that predict the ranking of the algorithms~\citep{XuEtAl12,KerEtAl18}, formulating the problem as a recommendation task~\citep{MisSeb17} and other approaches.

\end{itemize}
Additionally, for algorithm selection, there is a need for two additional, problem specific components:
\begin{itemize}
    \item \textbf{Feature computation:} Representative features of the problem instance are computed and used as input to the learned selector. These features can be hand-crafted or learned from the data. The choice of features is crucial for the performance of the algorithm selector. For example, the SATzilla features are well-known to be a good representation of \gls{sat} instances~\citep{HutEtAl14,ShaHoo24}, while for machine learning datasets, there exists many features, such as the basic descriptors of~\citet{OztEtAl22} to more complicated features, that include advanced statistics, such as the ones implemented in PyMFE~\citep{AlcEtAl20}.

    \item \textbf{Evaluation metric:} This is an important component of algorithm selection, as it is used to evaluate the performance of the algorithm selector. While there exist broadly applicable metrics such as the performance of the \gls{vbs} and \gls{sbs}, their definition depends on the specific problem.

    Therefore, a problem-specific evaluation metric must be chosen that represents the performance of the algorithm. This can be, for example, accuracy, precision, recall, F1-score, AUC, running time and more, depending on the use-case.
\end{itemize}
An overview of the algorithm selection pipeline is presented in~\cref{fig:ch02:asf_pipeline}.

\subsection{Algorithm selection versus multi-class classification}
A common mistake among newcomers to algorithm selection is to treat it as a standard multi-class classification problem.
Although an algorithm selector predicts one algorithm from a finite set and

can therefore be seen as performing a multi-class prediction task, training it as an ordinary multi-class classifier can yield sub-par performance, because it discards the performance of the algorithms relative to each other.

To see why, consider an instance where the performance gap between the best and the second-best algorithm is small.
In that case, selecting the second-best algorithm is a reasonable error.
A plain multi-class classifier, however, treats this outcome as equally wrong as choosing an algorithm that performs very poorly on the instance.
As we show in our ASlib experiments (\cref{sec:ch10:aslib_appendix}), multi-class classifiers can indeed perform far below the other methods in practice.

\subsection{Performance prediction versus ranking}

To model performance, one should account for the distribution of the performance, which can require preprocessing of the labels, such as log-transformation~\citep{HutEtAl14}. However, EPM-based algorithm selection is often not the practically best approach, essentially because accurately predicting exact performance values is generally a harder task than determining the relative ranking of algorithms.

\section{Bayesian optimisation}
\label{sec:ch02:bayesian_optimisation}

This section introduces hyperparameter optimisation and Bayesian optimisation as a search framework for black-box objectives used in \cref{ch:ch06:dymbo,ch:ch08:noisy_oracle}.

\subsection{Hyperparameter optimisation}
\label{sec:ch02:hpo}

\new{Hyperparameter optimisation} (HPO) seeks settings of a learning algorithm that minimise its validation loss~\citep{BisEtAl23}. Let $\algo$ be a learning algorithm, $\configurationSpace$ its hyperparameter configuration space, and $\mathcal D_{\mathrm{train}}$ and $\mathcal D_{\mathrm{validate}}$ fixed training and validation data. For $\configuration\in\configurationSpace$, let $\algo_{\configuration}$ denote the algorithm with that configuration. The HPO objective is
\begin{equation}
\label{eq:ch02:def-hpo}
    f(\configuration) =
    \mathcal L(\algo_{\configuration},\mathcal D_{\mathrm{train}},
    \mathcal D_{\mathrm{validate}}),
    \qquad
    \configuration^* \in \argmin_{\configuration\in\configurationSpace}
    f(\configuration),
\end{equation}
where $\mathcal L$ denotes the loss obtained by training on $\mathcal D_{\mathrm{train}}$ and evaluating the fitted model on $\mathcal D_{\mathrm{validate}}$. Cross-validation can replace a single split by averaging this loss over multiple training and validation splits. Randomised training can make evaluations stochastic; an expected validation loss then defines the underlying objective.

Hyperparameters specify choices such as a learning rate, a regularisation strength, or a model family, rather than the model weights fitted during training. Their domains can be continuous, integer-valued, or categorical. A configuration space can also be conditional: a parameter may only be active when a particular model family or component is selected. HPO is therefore a black-box optimisation problem whose search space need not be a simple continuous box. Its evaluations are often expensive because each configuration requires fitting and validating a model.

For $d_c$ hyperparameters with individual domains $\mathcal C_h$, the admissible space satisfies $\configurationSpace\subseteq\mathcal C_1\times\cdots\times\mathcal C_{d_c}$. Equality holds for independent, unconstrained parameters; conditional parameters and constraints restrict the admissible configurations.

\subsection{Bayesian optimisation}
\label{sec:ch02:bac_bo}

Bayesian optimisation (BO)~\citep{Mockus12b,Garnett23,Frazier18b,Kushner62,Kushner64b} is a family of surrogate-based algorithms for efficient global optimisation of black-box problems.
Let $f:\configurationSpace\rightarrow\mathbb R$ be the black-box objective to be minimised over the search space $\configurationSpace$. The optimiser can query $f(\configuration)$ at selected configurations, but is not supplied with an analytical expression or derivatives of $f$. Given a budget of $B_{\mathrm{eval}}$ evaluations, it selects $n_{\mathrm{eval}}\leq B_{\mathrm{eval}}$ configurations, potentially using earlier observations to choose later ones, and returns an incumbent. For noiseless evaluations, the best evaluated configuration is
\begin{equation*}
    \configuration^{\mathrm{inc}} \in
    \argmin_{\configuration\in
    \{\configuration^{(1)},\ldots,\configuration^{(n_{\mathrm{eval}})}\}}
    f(\configuration).
\end{equation*}
In practice, a budget may instead limit wall-clock time. Evaluations may also be noisy, in which case an observed value is a random outcome and the objective can be defined as its expectation. Limited evaluations require a balance between exploring unknown regions and improving on promising configurations~\citep{Garnett23}.

Typically, BO consists of three main components: an \emph{initial design}, \emph{i.e.}, in HPO, a set of candidate hyperparameter configurations $\mathcal C_{\mathrm{obs}} = (\configuration^{(1)},\ldots, \configuration^{(n_0)})$ and their evaluations
$f(\mathcal C_{\mathrm{obs}}) = (f(\configuration^{(1)}),\ldots, f(\configuration^{(n_0)}))$; a \emph{surrogate model} (fitted to the
observations) that returns an approximation $\hat{f}(\configuration)$ of the unknown loss function $f(\configuration)$ while capturing the uncertainty in the prediction $\hat{\sigma}(\configuration)$ on unobserved points in the search space; and an \emph{acquisition function}, which is optimised to suggest candidate solutions to be evaluated next, usually balancing exploration and exploitation of the search space.
BO then evaluates the most promising candidate solutions.
To approximate the expensive objective function, BO typically employs a Gaussian process (GP) model as the surrogate. The GP model defines a distribution over functions on the configuration space $f(\configuration)\sim\mathcal{GP}_f(\mu(\configuration),k_{\mathrm{GP}}(\configuration,\configuration'))$, where
$\mu(\cdot)$
is a mean function and
$k_{\mathrm{GP}}(\cdot,\cdot)$
is a covariance function. If we consider an observation model
$y_j = f(\configuration^{(j)}) + \varepsilon_j$
with normally distributed noise,
$\varepsilon_j\sim\mathcal{N}(0,\sigma^2_\varepsilon)$,
the predicted value by the GP model at one unknown configuration
$\configuration$ will also follow a normal distribution with mean
$\mu(\configuration)=\mathbf K_{\configuration,\mathcal C_{\mathrm{obs}}}(\mathbf K_{\mathcal C_{\mathrm{obs}},\mathcal C_{\mathrm{obs}}}+\sigma^2_\varepsilon \mathbf I)^{-1}\mathbf y$ and variance $\sigma^2(\configuration)=k_{\mathrm{GP}}(\configuration,\configuration)-\mathbf K_{\configuration,\mathcal C_{\mathrm{obs}}}(\mathbf K_{\mathcal C_{\mathrm{obs}},\mathcal C_{\mathrm{obs}}}+\sigma^2_\varepsilon \mathbf I)^{-1} \mathbf K_{\mathcal C_{\mathrm{obs}},\configuration}$,
where $\mathbf y=(y_1,\ldots,y_{n_0})$ is the vector of observations, $\mathbf K_{\mathcal C_{\mathrm{obs}},\mathcal C_{\mathrm{obs}}}=[k_{\mathrm{GP}}(\configuration^{(j)},\configuration^{(j\prime)})]_{\configuration^{(j)},\configuration^{(j\prime)}\in\mathcal C_{\mathrm{obs}}}$ is the covariance matrix, and $\mathbf K_{\configuration,\mathcal C_{\mathrm{obs}}}=[k_{\mathrm{GP}}(\configuration^{(j)},\configuration)]_{\configuration^{(j)}\in\mathcal C_{\mathrm{obs}}}$ is the correlation vector for all samples.
GPs as a surrogate model inherently provide both the mean and the variance vector.

However, GPs are not the only surrogate model used in BO. Another common choice for a surrogate model are tree-based models,
such as random forests (RFs).
Tree-based models traditionally predict only the mean of the given data (\emph{e.g.}, in a regression setting).
In this case, the variance is defined based on the variance of the predictions of the leaves~\citep{HutEtAl11}.
With $e_{\mathrm{RF}}(\configuration)$ being the prediction of a tree $e_{\mathrm{RF}} \in \mathcal E_{\mathrm{RF}}$, we calculate the mean $\mu(\configuration)$ and variance $\sigma^2(\configuration)$ for a set of trees $\mathcal E_{\mathrm{RF}}$ as follows:
\begin{equation}
    \mu(\configuration)=\frac{1}{|\mathcal E_{\mathrm{RF}}|} \cdot \sum_{e_{\mathrm{RF}}\in \mathcal E_{\mathrm{RF}}} e_{\mathrm{RF}}(\configuration) \; ,
\end{equation}
\begin{equation}
    \sigma^2(\configuration)=\frac{1}{|\mathcal E_{\mathrm{RF}}|} \cdot \sum_{e_{\mathrm{RF}}\in \mathcal E_{\mathrm{RF}}} (e_{\mathrm{RF}}(\configuration) - \mu(\configuration))^2 \; .
\end{equation}
BO proceeds iteratively until a termination criterion is met. In each iteration, it optimises the acquisition function by repeatedly querying the surrogate model to generate a pool of candidate solutions. It then evaluates the most high-potential solutions (\emph{i.e.}, the solutions that maximise the acquisition function) from this pool,
refines the surrogate model based on the new observations, and updates the optimum if the new point improves upon the true function value of the best observation so far.

\subsection{Acquisition functions}
\label{sec:ch02:acquisition_functions}

For the acquisition functions below, we use the notation of \cref{ch:ch08:noisy_oracle}.

Given a black-box function $f:\sR^{d_c}\rightarrow\sR$, the goal of an optimiser is to find its minimum, denoted by $\configuration^*$, such that $f(\configuration^*)\leq f(\configuration)$ for every $\configuration\in\sR^{d_c}$. The optimiser iteratively samples configurations $\configuration_1, \configuration_2, ..., \configuration_n$, where $\configuration_t$ is the configuration sampled at iteration $t$.
At each iteration, the optimiser observes the performance $f(\configuration_t)$, producing the set of observations $\train=\{(\configuration_1, f(\configuration_1)), (\configuration_2, f(\configuration_2)),..., (\configuration_n, f(\configuration_n))\}$.

Bayesian optimisation~\citep{Garnett23} uses a surrogate model to decide on the next configuration to sample. At iteration $t$, the surrogate model $m$ takes an unseen configuration $\configuration$ together with the observation set $\train$ and estimates a predictive distribution for $\configuration$, typically summarised through a mean $\mu_m(\configuration)$ and variance $\sigma_m^2(\configuration)$.
GPs are a common choice for such a surrogate model, but random forests~\citep{HutEtAl11} and other machine-learning techniques that can provide uncertainty estimates are also used.

Following the fitting of a surrogate model, an acquisition function is used to determine the next point to sample, balancing exploration and exploitation by considering the predicted mean and variance. Here, we consider three popular acquisition functions. First, expected improvement (EI) quantifies the expected improvement in the known optimum by sampling a configuration $\configuration$; formally:
\begin{multline}
    EI(\configuration)=\mathbb{E}[max(0, f(\configuration^{\mathrm{inc}})-\mu_m(\configuration))]=\\(f(\configuration^{\mathrm{inc}})-\mu_m(\configuration))\cdot\Phi(\zeta)+\sigma_m(\configuration)\cdot\phi(\zeta)
\end{multline}

\begin{equation*}
    \zeta=\frac{f(\configuration^{\mathrm{inc}})-\mu_m(\configuration)}{\sigma_m(\configuration)},
\end{equation*}
where $f(\configuration^{\mathrm{inc}})=\min_{j=1, 2, ..., n} f(\configuration _j)$ is the best observed function value up to iteration $n$, also known as the incumbent.
Similarly, probability improvement (PI) quantifies the probability that configuration $\configuration$ improves over the known optimum:
\begin{equation*}
    PI(\configuration)=\Pr(f(\configuration^{\mathrm{inc}})-\mu_m(\configuration) > 0)=\Phi(\zeta)
\end{equation*}
Finally, the lower confidence bound (LCB) is the weighted sum of the predicted performance $\mu_m(\configuration)$ and the uncertainty $\sigma(\configuration)$:
\begin{equation*}
    LCB(\configuration)=-(\mu_m(\configuration)-\beta_{\mathrm{LCB}}\sigma_m(\configuration))
\end{equation*}

The acquisition function $\alpha_t$ is then optimised to find a candidate configuration $\configuration_{\mathrm{next}} \in \argmax_{\configuration\in\sR^{d_c}}\alpha_t(\configuration)$. Different methods have been proposed to optimise the acquisition function, including local search, evolutionary algorithms and gradient-based methods. Since evaluating the acquisition function is relatively cheap, many such evaluations can be used to obtain a strong candidate. The candidate is then evaluated on the target function $f$, after which $\train$ is updated as $\train=\train \cup \{(\configuration_{\mathrm{next}}, f(\configuration_{\mathrm{next}}))\}$. This process continues until a pre-defined evaluation budget is exhausted.
